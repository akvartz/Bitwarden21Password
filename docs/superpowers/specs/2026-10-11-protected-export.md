# M2 protected Chrome export slice

Status: implementation design. Builds on the accepted Go migration design.

## Scope and decisions

Deliver an experimental Chrome CSV to Bitwarden JSON conversion with explicit review in one process, exact local value checks, and private no-clobber Linux output. Linux is the native test platform. macOS output fails closed pending ACL/volume-policy review and native tests; Windows output fails closed until a reviewed DACL implementation and VM tests exist. Both retain read-only commands and build coverage. Provider import acceptance remains a separate pending gate. This slice does not complete all M2 qualification.

The alternatives were a persisted review token, a command-line blanket acceptance switch, and an in-memory session. Choose an in-memory session: fewer secret-bearing artifacts, no reusable token, and a direct binding between displayed review and execution. There is no saved session, automation bypass, or background service.

## Engine contract

Keep Document immutable. Retain original Chrome headers separately from normalized matching headers. Never trim cell values or reinterpret notes. A private Job captures the document, canonical source-order selection, target profile `chrome-to-bitwarden-json-v1`, absolute output-parent spelling resolved at construction, and exact review issues. Job is a handle to shared private pointer state, so copying its exported value cannot duplicate mutex/approval authority. The parent inode is opened at commit, not pinned while waiting for approval; active same-user filesystem substitution remains outside the boundary. Public DTOs are deep copies and cannot change execution.

`Document.NewJob(target Format, selection []int, parent string) (*Job, error)` prepares a bounded payload and validates it before any filesystem writes. Existing Plan remains read-only and compatible. Jobs support only this route. Output bytes are not exposed through public DTOs. Use a 32 MiB output ceiling and the existing strict Bitwarden parser budgets; amplification beyond them fails safely before writing. These conservative output limits are separate from successful source parsing.

`Job.Review() Review` returns Plan, Profile, a source-independent random ReviewID, and Issues. ReviewID is a non-secret in-memory correlation identifier that rejects stale or cross-job review responses, not a persisted approval capability; never include it in the final receipt. `Issue` has ID, Code, optional Column and Records counts only. Always require `experimental-import`, code `experimental_import`, Column 0 and Records equal to the selected count. Every unfamiliar column adds `relocate-column-N`, code `concealed_custom_field`, with its one-based column and selected record count. Add per-column issues with affected selected-record counts: `provider-blank-name` / `import_name_placeholder`, `provider-blank-notes` / `import_notes_null`, `provider-empty-username` / `import_username_absent`, `provider-empty-password` / `import_password_absent`, and `provider-empty-url` / `import_uri_removed`. Blank means ECMAScript trim produces empty (including U+FEFF); empty credentials/URLs means exactly empty, never whitespace-only. Emit these only when affected records exist. The local JSON preserves originals; these issues describe downstream import changes. The separate sampled import-rejection issue below accounts for blank-password/name rejection. Unknown-column relocation issues are emitted only when selected records exist. Add `provider-import-rejection` / `import_sample_rejected` with selected-record count if all sampled items at indices 0, floor(n/2), and n-1 have a name that is exactly `--` or ECMAScript-blank, and an ECMAScript-blank password. This mirrors the inspected provider badData guard, including whitespace-only passwords; skip for n=0. For more than 7,000 selected records, add `provider-large-export`, code `import_item_limit`, Records equal to the selected count: the inspected cloud individual-import server path rejects larger batches, while published limits differ. The always-required experimental issue also explains that encrypted field-size limits vary by provider version, so generated JSON can be rejected despite local validation; never truncate to fit an assumed plaintext cap. No value, path, arbitrary label or source hash appears in a report.

`Job.Approve(reviewID string, ids []string) error` requires the exact current ReviewID and accepts exactly the required issue-ID set (no missing, extra or duplicate IDs) once while planned. Failure leaves planned; success transitions to approved. `Job.Commit(ctx context.Context) (Receipt,error)` atomically claims approved -> writing before I/O; any replay/concurrent attempt fails. Completion, failure and cancellation are terminal. A copied public review or an approval for another Job cannot authorize it. The private output parent is captured at NewJob time and cannot be changed by Commit.

`Job.State() string` returns a fixed state. Receipt contains a safe Plan updated to state `output_validated`, Profile, generated JobDirectory basename and fixed FileName. OutputEmitted is true only on successful completion. DestinationImportVerified remains false. Remove planned-only caveats from a successful receipt; retain coverage/provider caveats. There is no completion receipt on failure, including a failure after publication.

JSON contains encrypted:false, folders:[], and login items in selected source order. Each item has type:1, exact name, notes when the note column exists, login.username/password, and one URI preserving even an empty string. Unknown columns become type:1 concealed custom fields with original header strings and exact values, including empty strings. Duplicates remain separate. Do not invent folder IDs, dates, account IDs or metadata. Compare decoded output against source cells using an independently structured validator, including count/order/custom-field labels/type, credential bytes and note absence. JSON encoder escaping does not change decoded values.

## Protected output boundary

`internal/protectedoutput.Write(ctx context.Context, parent string, payload []byte) (Result,error)` owns filesystem operations. Result contains only generated JobDirectory and fixed FileName; Error.Code is allowlisted. Migration maps errors to safe fixed codes. No source-path access or deletion exists here.

On Linux, open the existing parent with os.OpenRoot. Require the opened directory to be owned by the effective user and not writable by group/others; use the opened handle, not a pre-stat. Create a cryptographically random single-component job directory (0700) without reusing any existing name. Open its root and create `.bitwarden.json.partial` exclusively (0600). Verify effective modes. Write with cancellation checks, handle short writes, Sync, seek and compare bounded bytes through the same opened handle, and check Close.

Publish a complete inode using Root.Link(partial, `bitwarden.json`), which must not overwrite an existing entry. Do not use replacing Rename. Remove only the owned partial entry on the success path, then sync and close job and parent directory handles and roots. Any error or observed cancellation returns failure, never a completion receipt. Leave private artifacts on failure; do not recursively clean up, delete arbitrary substituted entries, retry a failed commit, or overwrite old jobs. A failure after linking can leave a complete file without a completion receipt. Users must treat such files as unverified. Filesystem support for links/sync is required; unsupported operations fail closed.

Rooted handles constrain traversal and remain anchored through path renames. The privacy boundary is other users on an ordinary local Unix filesystem with the checked permissions; it does not isolate a compromised process, root, or another process running as the same user. Root alone does not make mkdir/open atomic against a same-user attacker. No crash-durability or filesystem-ACL qualification is claimed beyond successful sync calls. No plaintext temporary file outside the private job directory. Hold parent/job *os.File directory handles before publication for sync and checked close; Go1.26 Root.Close discards underlying syscall close errors, so its return is not equivalent close evidence. Linux/macOS cross-build results do not qualify filesystem behavior.

## CLI

Add `convert --input PATH [--from chrome-csv] --to bitwarden-json --output-dir DIRECTORY [--select 1,3] [--json]`.

RunContext(ctx,args,stdin,stdout,stderr) shares the current reader and validation rules; retain Run for compatibility. Convert emits a safe review first, including every required issue ID, and a fixed approval instruction. Read at most 64 KiB from one input line. The exact response is `approve REVIEW_ID ID [ID ...]` with precisely the displayed IDs. EOF before a complete newline, decline, malformed input, pre-commit read/report errors and pre-commit cancellation produce no export. A conforming reader may return the complete final newline together with EOF; accept that completed line. Non-EOF read errors still fail. No `--yes`, `--force`, persisted token, or accepting arbitrary issue IDs. Interactive text explains that output is plaintext and provider acceptance is unverified; JSON mode emits typed review and completion events and still requires the same input response. JSON events are compact newline-separated objects `{event:"review",review:...}` then `{event:"completed",receipt:...}`; instructions go to checked stderr. Only a successful completion event identifies the generated basename and fixed filename, relative to the user-supplied directory.

Install SIGINT/SIGTERM cancellation handling only for convert; read-only commands retain normal OS signal termination because they do not honor the conversion context. Retain main's SIGPIPE policy. Cancellation during approval must return without producing output. The CLI does not close a caller-owned input stream; if a generic reader is blocked, any bounded read goroutine is limited to one per active invocation and the caller owns unblocking it. Exit 0 success/help; 2 arguments; 3 rejected/unsupported input, approval, state or platform; 1 I/O/validation/cancellation. All diagnostics are fixed codes. Check context after completion reporting too. A failed or interrupted final report may occur after a valid export and already-emitted completion event; return failure, document that it is not a successful CLI invocation, and do not retry automatically. Signal termination of read-only commands uses normal OS signal exit statuses, outside the table of ordinary return codes.

## Evidence and qualification

Synthetic RED edge cases precede implementation. Test exact independent literal JSON values, custom labels/empty cells, duplicate multiplicity, selection, source immutability, approval tampering/replay/concurrency, output expansion, private modes, symlink/hardlink collisions, injected write/sync/close/read/link failures, cancellation at publication boundaries, and safe process output. Native Linux tests and cross-builds are separate evidence. Actual provider import and native macOS/Windows tests remain pending. No installs, Rust changes, releases, or merge.
